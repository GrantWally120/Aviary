# Aviary test kit

How Aviary gets tested in the real app without touching Grant's profile or fighting him for the
mouse. Built during Phase 5 M2 (12 Sep 2026); HANDOFF §5 explains why each piece exists. Read
the **container** box there first: every tool here runs inside the Claude app's MSIX container,
where `%LOCALAPPDATA%` is virtualized, so tests must use a scratch profile.

## Build a test copy

```
dotnet publish src/Aviary/Aviary.csproj -c Release -p:Platform=x64 -p:RuntimeIdentifier=win-x64 ^
  -p:SelfContained=true -p:WindowsAppSDKSelfContained=true -p:WindowsPackageType=None ^
  -p:PublishSingleFile=false -p:PublishTrimmed=false -p:PublishReadyToRun=false ^
  "-p:PublishDir=C:/Users/user/Documents/Claude CoWork Enclosed/Zoo/tools/test/pub/"
```

Never publish over `publish/Aviary` while Grant's copy is running from it. From PowerShell use
forward slashes in PublishDir: a trailing `\"` swallows the rest of the arguments.

## The pieces

| File | What it does |
|---|---|
| `launch-m2.ps1 -Profile name [-Fresh] [-SettingsJson '{…}']` | Launches `pub/Aviary.exe` with `AVIARY_PROFILE_DIR=profiles/<name>` and `AVIARY_TEST_BROWSER_ARGS=--remote-debugging-port=9222`. Seed `{"improvementCollection":"true"}` to read its diagnostics. |
| `launch-quiet.ps1 -Profile name [-Fresh] [-SettingsJson '{…}'] [-Port 9333] [-Size WxH]` | **(M4.5) The launcher to use while Grant is at the PC.** Starts `pub/Aviary.exe` minimised and inactive (CreateProcess, SW_SHOWMINNOACTIVE — also a standing bug-50 check), then restores it at the BOTTOM of the z-order without activating. Aviary activates itself during start-up anyway, so the script checks and, if it has the foreground, minimises it (Windows hands focus back to Grant's window) and restores it inactive again — reported as `took-focus-and-gave-it-back`. **Port 9222 is taken by Grant's Chrome on this machine (19 Sep): use `-Port 9333` and `CDP_PORT=9333` for cdp.js.** |
| `drag-window.ps1 -ProcessId <pid> [-HoldMs 1200]` | **(M4.5, bug 67) DESKTOP INPUT — guard.ps1 must pass (it checks 30 s itself).** Lifts the test window above everything WITHOUT activating it (TOPMOST — SetForegroundWindow is refused to a background process), drags it by the toolbar's drag area with mouse_event for ~HoldMs, puts the cursor back, minimises + restores it inactive so Windows hands the foreground back, and parks it at the bottom. A real Windows move loop: it holds Aviary's dispatcher, which the minute sample reports as `stallsWhileWindowHeld`. |
| `hit-probe.ps1 -ProcessId <pid> [-Names "Minimise,Close"] [-Extra "x,y;x,y"]` | **(M4.5)** What Windows answers to WM_NCHITTEST at named controls (found through UI Automation) or at screen points — HTCAPTION, HTCLIENT, HTMAXBUTTON, HTTOP… No input is sent. How the Liquid Glass caption-button attempt was judged (HANDOFF §8). **In PowerShell, `$t` and `$T` are the SAME variable** — a TreeScope in `$T` overwrote a path in `$t` once (19 Sep). |
| `frames.ps1 -ProcessId <pid> -Crop "x,y,w,h" -Then "<command>" [-Ms 700] [-MaxFrames 18] -Out sheet.png` | **(M4.5)** Films an animation: PrintWindow as fast as it goes while `-Then` runs, keeps each capture that differs from the one before, and lays them out top to bottom as ONE contact sheet with each frame's time. How the tab chip's glide and gel stretch, a tab growing in and the loading line were checked. **PrintWindow barely refreshes WebView content**, so a CSS transition inside a page shows as 2-3 frames: sample it from inside the page instead (`cdp.js eval` with a requestAnimationFrame loop reading `getComputedStyle`). Pass `-Then` from PowerShell when it holds quotes (a title with a space). |
| `motion-session.ps1 -Profile name -Settings '{"look":"Liquid Glass"}' [-Rounds 2]` | **(M4.5)** Every animated path in a fresh quiet instance: tabs opened, switched (UIA Toggle), closed (`window.close()` - DevTools Ctrl+W only reaches a window in front), sidebar shown/hidden and its panes, Settings panes, four look swaps through the real dropdown. Then prints the minute samples, stalls over 50 ms, crash reports and swallowed errors, saves `shots/<profile>-end.png` and closes the instance. Run once per style: Classic (Smooth Flight), Liquid Glass (Fluid), `"reduceMotion":"true"`. A CSS selector for a value with a space needs single quotes inside: `[data-v='Liquid Glass']`. |
| `flyout-geometry.ps1 -ProcessId <pid> [-Ids MenuButton,PageSettingsButton,…]` | **(M4.7, bug 75) Run this after touching `Motion.cs` or `ThemeOpenPopups`.** Opens each flyout and reports how far its CONTENT sits from its own `PopupWindowSiteBridge` window. Healthy is the drop shadow's `(10,2)`; anything else means the menu is drawn in one place and hit-tested in another, so every click on it counts as a click OUTSIDE and the menu just dismisses. M4.6 read `(867,44)` for the app menu and `(285,41)` for Aa. No input is sent. It picks the LAST popup window it finds, so close any tooltip first — a tooltip is a popup too, and it stole the match once. |
| `menu-click.ps1 -ProcessId <pid> [-Row 400] [-Col 137]` | **(M4.7) DESKTOP INPUT — `guard.ps1` must pass.** One real mouse click at a point inside the open flyout's own window, which is the ONLY thing that can tell whether a menu item actually answers: UIA `Invoke` goes through the InvokePattern and `PostMessage(WM_LBUTTONDOWN)` does nothing in WinUI 3, so both "work" on a broken build. Lifts the popup topmost without activating (a background process cannot `SetForegroundWindow`), clicks, puts the cursor back, parks the windows and stamps `lastinput.txt`. **Aim it from a capture of the popup, never from the UIA rect** — the UIA rect is the thing under test. |
| `bloom-frames.ps1` | **(M4.7) DOES NOT MEASURE THE BLOOM — do not use it as evidence.** It counts every capture that differs from the last, and a menu repaints for hover and focus whether it bloomed or not: on 21 Sep the reduce-motion control (no bloom at all) scored 26 against motion's 14. M4.7 and M4.8 both cited it without ever running a control; those claims are struck through in HANDOFF. Kept as the record of the mistake. |
| `bloom-ramp.ps1 -ProcessId <pid>` | **(M4.9) Also cannot isolate the bloom — kept as the record of what was tried.** Tracks the popup's brightness from the moment its window exists. It ramps with or without Aviary's bloom, because **WinUI fades every flyout in by itself**. No capture from outside the process can tell Aviary's added scale from WinUI's own fade. |
| **`AVIARY_MOTION_TEST=1`** | **(M4.9) What DOES prove the bloom runs.** Set in the environment before launch (like `AVIARY_CRASH_TEST`); every `Motion.Bloom` then writes one `"k":"bloom"` line to `perf.jsonl` with the style, the element and its size. Expect ONE line per menu open, on a `Border` (the presenter's template root — the popup's own root would be bug 75 again), with a real size. |
| `saver-modes.ps1 [-Seconds 6]` | **(M4.9)** Memory saver's four modes and both migrations, one fresh profile each: Off must sleep NOTHING even with `AVIARY_SLEEP_TEST` set; Chill/Balanced/Aggressive must each sleep; a stored `"true"` must come up as Balanced IN THE STORE and `"false"` as Off. |
| `minimise-sleep.ps1 [-Mode Aggressive]` | **(M4.9)** Aggressive sleeps background tabs the moment the window is minimised. Deliberately run WITHOUT the sleep test hook, so the idle timer is a real 5 minutes and cannot be what sleeps the tab. Run it with `-Mode Balanced` as the control: minimising must sleep nothing. `ShowWindow` on the test window only — not desktop input. |
| **`AVIARY_FRAMES_TEST=<seconds>`** | **(M4.9)** Frame timing reports every N seconds instead of every minute. On Grant's 240 Hz screen a healthy line reads ~240 frames a second with a 4.17 ms median. |
